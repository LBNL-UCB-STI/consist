Command Instrumentation: Product Direction and Market Exploration¶

Status: internal product exploration; no implementation decision

Decision to explore: Whether Consist should offer a low-friction CLI that runs an arbitrary terminal command while recording an explicit provenance boundary, and whether this should precede broad shared-artifact-registry work.

Executive view¶

consist exec has a credible chance to be Consist's strongest adoption wedge. It gives a scientist useful, durable provenance without requiring them to turn a working script into a Python callable, write a workflow graph, or first adopt a shared catalog. The user declares the inputs and outputs that matter, Consist runs the command, and the resulting record is immediately searchable, hash bound, and lineage-capable.

The user-facing pitch is: prefix the command you already run with consist exec, declare what goes in and what must come out, and receive a verified, searchable record—plus a clear answer to what changed since the last named run—without a refactor, DAG, or pipeline file.

This is deliberately not a claim that arbitrary shell commands can be made fully reproducible by observation alone. A command wrapper should make the declared boundary trustworthy, preserve its limits, and provide a path into the existing Tracker.run(...), container, recovery, and future registry surfaces.

The publication-facing honesty sentence should be equally direct: Consist records what users declare and verifies declared results; it does not guess complete dependency capture. This keeps the internal pilot useful without overclaiming automatic reproducibility in JOSS or conference material.

The proposed prioritization is:

  1. Validate command instrumentation as an adoption wedge.
  2. Use explicit artifact roles/names in recorded runs to discover the registry semantics people actually repeat.
  3. Build shared registry capabilities only when cross-run discovery, aliasing, custody, or handoff are demonstrated needs.

This sequencing serves the current product goals of low-friction developer experience and a lightweight provenance layer. It does not replace the registry roadmap; it gives the registry high-quality, real usage evidence and an easier on-ramp.

Proposed user experience¶

The initial shape should feel like a normal command invocation with an explicit provenance envelope:

consist exec \
  --name nc-baseline \
  --input config=configs/baseline.yaml \
  --input population=data/population.parquet \
  --outputs-dir outputs/ \
  --cwd . \
  -- python launch_model.py --config configs/baseline.yaml

On success, Consist should create a run record and input/output artifact links. It should emit a compact machine-readable execution record, for example under the selected run directory, plus normal CLI-readable run and lineage records. The final terminal summary should name the run ID, state that every declared output was present and recorded, compare it with the most recent successful run of the same name in the same project, and print one next inspection command: consist show <run-id>. The comparison must name its baseline run ID and say which of command/configuration, declared inputs, and declared outputs changed; it must never imply that a same name means equivalent scientific intent.

--outputs-dir is an explicit output-boundary declaration, not process tracing. It records the regular files newly created or modified beneath that directory by their relative paths, using a manifest/logical-output representation where appropriate. It does not infer reads, watch unrelated directories, or silently collect arbitrary filesystem changes. --output key=PATH remains the precise option for one named product.

Before committing a costly command, users can inspect the boundary without creating a run or spawning a child process:

consist exec --dry-run \
  --input config=configs/baseline.yaml \
  --outputs-dir outputs/ \
  -- python launch_model.py --config configs/baseline.yaml

The dry-run report must show the resolved argv and working directory, each input's fingerprint, the expected output boundary, code-identity mode, any warnings or unresolved paths, and the selected comparison baseline when one exists. Existing regular-file argv tokens should appear as suggested inputs only. They affect neither identity nor lineage unless the user explicitly names them with --input or promotes the displayed set with --accept-suggested. Suggestions must exclude the executable, -/stdin, URLs, and paths that are already declared as outputs; shell-mode commands receive no inferred inputs.

The command boundary must use argv execution after --, not construct a shell string. An explicit --shell mode is available for pipelines, redirection, and shell expansion, but it must be loud: record the script string, resolved shell executable, and shell=true in the run; warn that argv-level input suggestions are unavailable; and never silently change the default parsing or quoting semantics.

MVP bootstrap: a stable local project home¶

consist init should create a minimal .consist/ project home with the local tracker and run-record locations. From any subdirectory, Consist should walk upward to the nearest .consist/ directory; explicit tracker/run-directory arguments still take precedence. The CLI must report the resolved project root in --dry-run and consist show output so users do not have to guess where a record was stored.

This is deliberately a marker and discovery rule, not a configuration language: no profiles, command recipes, environment policy, or implicit artifacts belong in the MVP. It removes routine tracker-location friction while retaining an unambiguous local provenance ledger for terminal and Python work.

Deferred post-pilot: project configuration and convention discovery¶

Only after the bootstrap has been tested should Consist add a configuration file. Pilot evidence must show that repeated operational flags—not incorrect artifact declarations—are the material adoption obstacle.

Command instrumentation needs a project-level convention so that terminal commands and Python code join the same local provenance ledger without every invocation repeating database, run-directory, and policy flags. Support both a language-neutral .consist.toml and [tool.consist] in pyproject.toml; prefer the former in mixed-language repositories.

# .consist.toml
version = 1

[tracker]
db_path = ".consist/provenance.duckdb"
run_dir = ".consist/runs"

[identity]
code_root = "."
require_git = false

[commands]
log_retention = "on-failure"
environment_allowlist = ["PATH", "LANG", "OMP_NUM_THREADS"]
default_output_policy = "require-present"

[profiles.cluster]
run_dir = "/scratch/${USER}/my-project/consist-runs"
environment_allowlist = ["SLURM_JOB_ID", "OMP_NUM_THREADS"]

The corresponding Python entrypoint should be explicit and small:

from consist import open_project_tracker

tracker = open_project_tracker()

consist exec and open_project_tracker() must resolve the same effective configuration. The intended precedence is:

explicit CLI/API arguments
→ explicit --config / CONSIST_CONFIG
→ .consist.local.toml (ignored, machine-specific)
→ .consist.toml (committed project convention)
→ [tool.consist] in pyproject.toml

Resolve relative paths against the selected config file, never against the caller's current directory. Provide consist config show --resolved to display the effective non-secret configuration and which source supplied each value.

Configuration is not scientific identity¶

The project config establishes operational convention: tracker location, run directory, mounts, profiles, log policy, and a safe environment allow-list. It must not silently become a cache input or define a second workflow language. Each run independently records the identity-bearing facts: declared input hashes, exact argv, command-specific configuration files, code identity, and selected environment digest. A profile change can be recorded as execution metadata; it changes the result identity only when it changes one of those declared inputs or execution facts.

Keep commands limited to defaults and policy. Do not add named command recipes, dependency inference, or implicit outputs in this config. Those would recreate a workflow DSL and blur the explicit boundary that makes the feature trustworthy.

What Consist would record¶

Required v1 facts¶

  • Exact argv list, working directory, start/end timestamps, duration, process exit status, and signal/termination outcome when available.
  • Declared input paths and output paths, their role keys, and the applicable content or manifest fingerprints.
  • Code identity when it can be established safely: repository revision and dirty state, or an explicit identity mode that says it was unavailable. It must not invent caller identity for a non-Python command.
  • A selected, allow-listed environment identity as a digest rather than raw secret-bearing environment values.
  • Paths to captured stdout/stderr files, with truncation/retention policy made explicit.
  • Post-exit output checks. Exit zero alone is not enough: a declared output must exist and pass the normal artifact admission/hash step before the run becomes successful.
  • An interruption outcome. The wrapper must record its best observed child signal/exit state on Ctrl-C and leave an actionable, reconcilable running record if the wrapper itself is killed before finalization.
  • The comparison baseline (or its absence), its run ID, and field-level classifications for command/configuration, declared inputs, and declared outputs. A comparison is evidence for inspection, not an equivalence claim.

Declared in-place mutation: simulation checkpoints and persistent stores¶

Legacy tools and complex simulations frequently update a persistent store or checkpoint file at the same path that they consume. A prime example is simulation checkpoint-resume workflows (such as ActivitySim's cli_resume mode), where a base execution initializes a multi-gigabyte pipeline store (pipeline.h5 or pipeline.parquet), and subsequent calibration or continuation steps run resume_after by updating that store in place.

Without explicit mutation tracking, client harnesses are forced to write bespoke pre- and post-execution inspection logic to hash internal checkpoint tables or make defensive copies of large files. Consist provides a clean, native provenance shape for this pattern via explicit declared mutation:

consist exec \
  --input config=configs/baseline.yaml \
  --mutate pipeline=outputs/pipeline.h5 \
  -- python -m activitysim run -c configs -d data -o outputs --resume-after trip_mode_choice

In the Python API, tracker.exec(...) accepts mutate mappings alongside inputs and outputs:

result = tracker.exec(
    name="resume_simulation",
    argv=[
        "python", "-m", "activitysim", "run",
        "-c", "configs", "-d", "data", "-o", "outputs",
        "--resume-after", "trip_mode_choice",
    ],
    inputs={"config": "configs/settings.yaml"},
    mutate={"pipeline": "outputs/pipeline.h5"},
    outputs={"final_trips": "outputs/final_trips.csv"},
)

--mutate key=PATH (or mutate={"key": PATH}) means Consist requires and fingerprints the pre-state before spawn, then fingerprints and logs the post-state as a fresh output artifact after successful exit. The two records share a logical role key and URI but represent distinct, immutable artifact records in the provenance ledger:

run_042
  input   pipeline (pre-state)  → artifact A (before fingerprint)
  output  pipeline (post-state) → artifact B (after fingerprint)

This remains true even when the store bytes are unchanged: Consist creates a fresh output artifact record and deduplicates identical content separately in storage. It reports that case as pipeline: unchanged (<fingerprint>), not as an absent output or silent no-op. The command must reject a path simultaneously declared with --input and --output; --mutate is the unambiguous intent declaration.

Rules for mutation tracking:

  • The target must exist before launch. Creation belongs to --output; do not add --mutate-may-create in the initial increment.
  • Use full content fingerprints for the transition in the first increment. Fast structural or table-level digests (e.g. for HDF5 groups or Parquet partitions) may be layered in later via driver-specific plugins, but must never be presented as byte-transition evidence without a verified contract.
  • Acquire an exclusive advisory lock for the target and fail before spawn when it cannot be acquired. Do not pretend a before/after hash comparison can detect an interleaving writer; it cannot.
  • A deleted or unreadable post-state is treated as a failed declared output.
  • Generic host-command caching remains disabled. A future safe mutation cache would have to restore the exact pre-state in an isolated workspace and control publication of the post-state.

The existing run-to-artifact link key does not need to change for this design: the pre-state and post-state are separate artifact rows. The existing same-artifact input/output conflict check in Consist remains a useful guard against callers accidentally reusing one in-memory artifact reference.

Explicitly deferred facts¶

  • Automatic discovery of every read and written file.
  • Dependency installation, sandboxing, containerization, or a claim of bit-for-bit replayability.
  • Cache reuse by default.
  • Automatic parsing of a model's semantic configuration or performance metrics.
  • A shared registry, remote service, or artifact custody transfer.

These are not omissions to conceal. They are the feature's honesty contract: the user attests to the computational boundary, and Consist verifies and records it.

Selling points¶

Immediate value for scientists and modelers¶

  1. Preserve a working workflow. Record a legacy Python, R, Julia, Java, C++, shell, or vendor executable without first refactoring it into a library API. This matters particularly for research models that are expensive or risky to restructure.
  2. Turn a terminal command into evidence. A successful run is tied to declared input bytes, expected outputs, the command, and an execution outcome—not merely a notebook cell, a shell history line, or a directory timestamp.
  3. Recover lineage when the workflow is only partly formalized. Once a few commands have explicit inputs and outputs, consist lineage, run search, and artifact validation become useful even before there is a DAG.
  4. Meet multi-language and black-box tools at their natural boundary. The value applies equally to a simulator binary, an R analysis, an Apptainer launch, a shell script, or a Python program.
  5. Avoid secret and path leakage by design. Store a scrubbed/digested environment identity and explicit logs, instead of indiscriminately copying process state.
  6. Catch plausible-looking failures. A command that exits zero but omits a declared metrics.parquet is a failed run with a visible reason, rather than a result silently lost in shell history.

Product and adoption value¶

  1. A short time-to-first-value path. The first useful interaction is a single prefixed command, not an API migration or workflow rewrite.
  2. A natural bridge to existing Consist value. Recorded outputs can use the same artifact hashing, validation, recovery, querying, and portable lineage constructs that native runs use.
  3. A credible upgrade path. A repeated command can later become a native Tracker.run(...) wrapper, a container run, a scenario step, or a promoted registry artifact without losing prior provenance.
  4. Better product discovery than registry-first design. Repeated names, roles, output types, and handoff patterns expose which registry aliases and policies users actually need.

Strong use cases¶

Use case Why the wrapper is strong What the user declares
Legacy regional model launch The model remains a script/binary with file-oriented inputs and outputs; refactoring risks changing behavior. Config, prepared demand/network inputs, output directory or named final products.
Calibration or parameter sweep trial Each trial needs comparison and provenance, but a full workflow engine is too much for an exploratory loop. Baseline inputs, parameter/config file, trial metrics and diagnostics.
Simulation calibration with config overrides (ActivitySim, MATSim, EnergyPlus) Simulations run as CLI commands against dynamically overridden YAML/CSV parameter sets; requires materializing config overlays into CLI flags without custom subprocess wrappers. Base config dirs, parameter overrides, data directory, declared outputs (e.g. final_trips.csv).
R/Julia/Stata/SAS analysis Native Consist decorators are not an option, but data-to-report provenance still matters. Input tables, script, rendered report and result tables.
Container or HPC launcher The outer command launches a container or scheduler submission; Consist can record the intended boundary and submitted-job evidence. Image reference, launch config, submission record; final outputs only when completion is observed.
Published-result reconstruction A user reruns one narrow analysis step and needs a defensible record without adopting an entire original pipeline. Source data/config, command, regenerated figure/table.
Checkpoint-resume simulation & store mutation (ActivitySim pipeline.h5, MATSim events) Simulation continuation steps update an existing pipeline or state store in place; copying multi-gigabyte stores obscures lineage and wastes disk. The less suitable cases are equally important: interactive GUI work; commands whose meaningful effects are hidden remote database mutations; long-running scheduler submissions whose completion cannot be observed by the local wrapper; and workflows where users need automatic scheduling, dynamic fan-out, or global DAG optimization. Those need adapters or workflow engines, not a misleading single-command abstraction.

Mixed-shape composition: Python, commands, and existing Consist applications¶

Command instrumentation must compose with native Consist steps through one run/artifact model. The public API should therefore be tracker.exec(...) and scenario.exec(...); consist exec is a thin frontend over the same command executor, lifecycle, output admission, recovery, and lineage implementation.

Scenario: baseline
├── Python run: prepare inputs        (cacheable)
├── Command exec: run simulator       (record-only in v1)
└── Python run: validate and summarize (cacheable)

with tracker.scenario("baseline", model="regional_model") as sc:
    prepared = sc.run(
        prepare_inputs,
        inputs={"raw": raw_input},
        outputs=["prepared"],
    )

    simulation = sc.exec(
        name="simulate",
        argv=["./model", "--config", "configs/baseline.yaml"],
        inputs={"prepared": consist.ref(prepared, "prepared")},
        output_sets={"model_outputs": model_output_set},
        execution_options=CommandExecutionOptions(cwd=workspace),
    )

    sc.run(
        summarize,
        inputs={"outputs": consist.ref(simulation, "model_outputs")},
        outputs=["report"],
    )

Every independently meaningful computation is a sibling step under the scenario header. Artifact references, not raw output paths, express the producer-to-consumer lineage; path staging remains an explicit runtime concern when an external tool requires a fixed filename. Native Python run(...) steps retain their existing per-step cache semantics. Generic command steps are record-only until a later cache contract is designed.

Four composition shapes¶

Shape Representation Why
A Python step calls a small helper command, such as a renderer or converter One run(...); store a bounded subprocess observation in its execution metadata. The Python function remains the meaningful computation. Adding a run node for every helper command creates lineage noise.
A command has distinct inputs, outputs, substantial runtime, or reuse value scenario.exec(...) as a sibling Python/command step. The command has a real provenance boundary, with its own exit status, logs, and artifacts.
A command requires materialized configuration overrides (e.g. simulation calibration) tracker.exec_with_config_overrides(...) Evaluates an external CLI simulator against dynamically materialized config overlays without custom subprocess wrappers.
A terminal-launched Python application already instruments internal work with Consist Delegated execution envelope plus child native runs. Captures terminal facts without duplicating the internal application's step lineage.

Composition with configuration adapters and overrides (tracker.exec_with_config_overrides)¶

In simulation calibration, parameter sweeps, and sensitivity analysis (e.g., ActivitySim, MATSim, EnergyPlus), models are executed as CLI processes, not Python callables. In calibration loops, each trial evaluates a candidate parameter vector (such as mode choice coefficients or model constants). Consist already provides domain configuration adapters (ConfigAdapter, ActivitySimConfigAdapter, ConfigOverrides) to parse YAML/CSV configurations, compute canonical config hashes, and materialize overrides into isolated overlay directories.

However, tracker.run_with_config_overrides(...) assumes the target is a Python callable (fn). Client code in activitysim-calibration was therefore forced to write hundreds of lines of custom subprocess wrapping (subprocess.run, stderr/stdout capture, exit code inspection, path reconciliation) in runner.py and _evaluate_real_activitysim_step just to connect materialized configuration directories to CLI invocations.

Consist bridges this gap by composing command execution directly with configuration adapters:

result = tracker.exec_with_config_overrides(
    adapter=adapter,
    base_config_dirs=[config_dir],
    overrides=overrides,
    command=[
        "python", "-m", "activitysim", "run",
        "-c", "{selected_root_dir}",
        "-c", "{base_config_dirs[0]}",
        "-d", "{data_dir}",
        "-o", "{output_dir}",
    ],
    template_vars={
        "data_dir": data_dir,
        "output_dir": workspace / "output",
    },
    inputs={"data": data_dir},
    outputs={"final_trips": "output/final_trips.csv"},
    mutate={"pipeline": "output/pipeline.h5"},  # optional checkpoint resume
)

Lifecycle and Semantics¶

  1. Config Canonicalization & Override Materialization: Consist canonicalizes the base configuration roots and writes the overridden parameters into a managed overlay directory (matching run_with_config_overrides).
  2. Dynamic Argv Template Substitution: Consist replaces declared placeholder tokens in the command argv list:
  3. {selected_root_dir}: The path to the materialized overlay configuration directory.
  4. {root_dirs}: The ordered list of all configuration roots (materialized overlay directory followed by base directories).
  5. {materialized_dir}: Alias for {selected_root_dir}.
  6. Any keys supplied in template_vars.
  7. Command Execution: Consist delegates execution to CommandExecutor, managing working directory, environment filtering, process group isolation, and bounded stdout/stderr logging.
  8. Declared Artifact Checks & Mutation Capture: On zero process exit, Consist verifies that declared outputs (such as final_trips.csv) exist, computes post-state fingerprints for declared --mutate targets (such as pipeline.h5), and admits them into the provenance ledger.
  9. Unified Provenance Record: Consist records a single run record binding:
  10. The canonical configuration identity and exact parameter override values (via the ConfigAdapter),
  11. The command execution facts (argv, working directory, exit status, duration, stdout/stderr retention),
  12. Input artifact digests, output artifact fingerprints, and pre/post mutation transitions.

This eliminates client-side subprocess runners entirely, decoupling model execution from the calibration orchestration loop while preserving complete provenance.

Deferred: delegated execution envelope¶

Delegated mode is deliberately outside the first pilot, but it is the likely dogfooding path for terminal-launched applications that already use Consist internally, including PILATES-shaped workflows. The generic pilot must not exclude those users by implying this exists today; it should validate opaque command recording separately, then design delegation as its own security/lifecycle increment.

An already-instrumented application needs a distinct mode:

consist exec --delegate -- python pipeline.py --scenario baseline

The outer command run is an execution envelope. It owns argv, working directory, process outcome, selected environment identity, and log policy. It passes a short-lived, narrowly scoped execution-context reference to the child process. The child joins the configured project tracker and creates its normal scenario/run tree below that envelope:

tracker = consist.connect_execution_context()

with tracker.scenario("baseline") as sc:
    prepared = sc.run(...)
    results = sc.run(...)

The context handoff should identify the already-resolved tracker configuration, parent/envelope run ID, run-directory policy, and a capability that expires with the launch. It must not contain secrets or let an arbitrary process attach to an unrelated run. A child process may only join an active envelope selected by the parent, and the persisted record must identify this delegated relationship.

Delegated mode is intentionally not an opaque-output command run. The internal children own their outputs and cache identities. The envelope may present an aggregate summary or a separately named final handoff artifact, but it must not log the same physical outputs again under competing producers. This prevents duplicate artifacts, ambiguous lineage, and cache ownership errors.

Deferred: shared executor contract¶

Do not refactor containers or existing Python execution into a new executor protocol to prove the adoption wedge. The prototype can implement a narrow tracker.exec(...) by using the existing run lifecycle around argv process execution. Once the pilot validates the command contract, consolidate the following execution surfaces only if doing so removes demonstrated duplication.

The target post-pilot shape is a shared ExecutionSpec / ExecutionResult and executor protocol rather than permanently maintaining a CLI-specific path:

  • PythonCallableExecutor backs existing run(...) behavior.
  • CommandExecutor owns argv process launch, bounded log capture, exit/status recording, and declared output checks.
  • Existing container execution becomes another executor implementation where appropriate, retaining its stronger image/mount identity contract.

All executors feed the same run creation, artifact admission, lifecycle hooks, lineage, recovery, and optional OpenLineage emission. This preserves one provenance universe while allowing the executor-specific facts to remain honest.

Deferred: terminal flow artifact routing¶

Flow routing is a follow-on usability pilot, not a prerequisite for the first valid command record. Its priority should be decided by observed user friction: repeated flag setup, output declaration, or artifact handoff may prove more important first.

Successive terminal commands need the ergonomic equivalent of consist.ref(...), without turning paths or a mutable notion of “latest” into provenance. Introduce a scoped terminal flow with named artifact slots:

consist flow start baseline

consist exec \
  --publish prepared=work/prepared.parquet \
  -- python prepare.py --out work/prepared.parquet

consist exec \
  --input prepared=@flow:prepared \
  --stage prepared=work/inputs/prepared.parquet \
  --publish simulation=work/simulation/ \
  -- ./run-model --input work/inputs/prepared.parquet --out work/simulation/

consist exec \
  --input simulation=@flow:simulation \
  --stage simulation=work/inputs/simulation \
  --publish report=work/report.html \
  -- python summarize.py --inputs work/inputs/simulation --out work/report.html

The selected flow is a scenario-like parent record plus a small durable flow-manifest. Each successful --publish adds a slot binding:

flow baseline
  prepared   → (producing run, artifact ID, content hash)
  simulation → (producing run, artifact ID, manifest-v1 identity)
  report     → (producing run, artifact ID, content hash)

@flow:prepared is a convenience selector only. Before execution it resolves to the exact producing run, artifact ID, and verified file/directory manifest; the consuming run persists that resolved reference as its input lineage. The flow alias itself is not the input identity. Therefore later inspection and replay retain the precise bytes consumed even if the slot is subsequently rebound.

--stage deliberately separates logical identity from the workspace path a tool needs. It uses the normal materialization/hydration rules to place the selected artifact at an explicit destination. This avoids treating a raw path as proof of provenance and keeps fixed-filename tools practical.

Flow rules¶

  • Flow aliases are local to one named flow, not global registry aliases and not a remote custody claim.
  • The initial concept uses single-assignment slots with explicit --replace-slot NAME, retaining the old binding in append-only history. The follow-on pilot must test retries and parameter sweeps before freezing this UX: a keyed/iteration-scoped publication form may be safer than repeatedly overwriting one canonical slot.
  • Resolve collisions, missing slots, ambiguous artifact keys, and failed materialization before spawning the command.
  • The default selector must never mean “the prior command” or “latest matching output.” Those become wrong after retries, parallel work, or multi-output steps.
  • An interactive shell may activate a flow through a short-lived environment variable, but --flow FLOW_ID must work in scripts and CI. The durable manifest, not shell state, is authoritative.
  • A flow should expose its exact bindings through consist flow show and let consist show/lineage traverse each resulting ordinary run.

This is deliberately a thin routing convenience, not a workflow DSL. It has no implicit dependency inference, scheduling, fan-out, retry policy, or cache policy. It makes terminal composition explicit while preserving the same artifact contract used by Python scenarios.

Competitive landscape¶

This is a capability comparison, not a claim that Consist should displace these tools. Most competitors are excellent at their intended layer.

Category / examples What users get Where consist exec differs Product implication
DVC Declarative stages with commands, dependencies, outputs, lockfiles, and reproduction/caching behavior. DVC's model is explicitly a pipeline/stage graph. Consist can record a command today without adding or maintaining a project pipeline definition, and can preserve richer local provenance/recovery semantics. Do not compete by recreating a DAG engine. Offer a path for commands that are not yet—or never should be—DVC stages.
MLflow Projects and Tracking ML-focused project execution plus tracking of runs, parameters, metrics, code, and artifacts; projects can be invoked from local directories or Git URIs. MLflow is strongest when the user adopts its experiment/project model and logs ML-oriented metadata. Consist's niche is general scientific artifacts, explicit lineage, content identity, and non-ML tools. Avoid an ML metric dashboard race. Make the command wrapper valuable to a simulator or scientific analysis with no training loop.
Snakemake / Nextflow Declarative workflow languages, scheduling, execution reports, and task-level provenance for established pipelines. They require a workflow description and manage task orchestration; Consist would instrument one pre-existing command without becoming the scheduler. Position the feature before formalization and at integration boundaries, not as a substitute for mature workflow engines.
Kedro / Dagster Python-oriented pipeline/asset abstractions, catalogs, orchestration, and external-process integration. These frameworks own the pipeline model; Dagster can launch shell work inside its orchestration context. Consist should remain usable when there is no framework-owned project. Build optional emitters/adapters later rather than imitating framework architecture.
Makefile plus README Lightweight command recipes and human-maintained notes, often adequate for a stable local workflow. Neither verifies that declared products exist after a run, fingerprints the exact input/output transition, or provides queryable lineage across reruns. Respect this as the low-complexity baseline; prove the added value with missing-output and changed-artifact evidence, not abstract provenance language.
ReproZip System-call-level experiment tracing and packaging for later reproduction, including command line, working directory, and files. Its goal is a much heavier portable reproduction bundle. Consist should record an explicit, queryable provenance boundary and only archive/copy artifacts when requested. The closest conceptual precedent validates demand, while illustrating why v1 must resist automatic “capture everything” scope.
OpenLineage A standard event model for job/run lifecycle and lineage; it is commonly emitted by orchestrators and integrations. It is an interchange/event contract, not a local command runner, artifact verifier, cache identity system, or recovery layer. Continue to treat OpenLineage as an optional outbound projection, not the execution core.

Relevant external evidence¶

  • DVC pipeline documentation describes stages through command, dependency, and output relationships; that is useful precisely because it is a maintained declarative graph, not an ad-hoc command recorder.
  • MLflow Projects provides a conventional project format and mlflow run for local or Git-based projects; MLflow Tracking organizes execution into runs with metadata and artifacts.
  • Snakemake reports and Nextflow trace observers demonstrate the reporting depth available once a workflow engine owns the task lifecycle.
  • Dagster's shell integration launches shell commands from an asset/orchestration context; it confirms the value of external-command boundaries but assumes Dagster ownership.
  • ReproZip's glossary describes tracing one or more command lines, while its unpacking documentation shows its deliberate emphasis on replay bundles and environment handling.
  • OpenLineage's specification defines lifecycle events for a run of a job. It is a useful interoperable emission target, not a substitute for Consist's local artifact contract.

Relationship to the object registry¶

The two ideas solve different moments in the lifecycle.

Question Command instrumentation Shared object registry
Primary user question “What exactly happened when I ran this?” “Which trusted artifact fills this role, where is it, and may I use it?”
First value A single existing command. A community agrees on roles, identity, location, aliases, and admission rules.
Authority Local execution record and explicit artifact links. Shared immutable identity, custody/admission evidence, durable locations, and alias policy.
Main risk Overclaiming discovery or reproducibility. Premature governance and semantic commitments.
Natural connection Declared output names/roles reveal registry candidates. Promoted artifacts can be fed back as explicit inputs to later command records.

Consist's portable provenance schema intentionally does not make itself an artifact registry or a complete execution-observation model. This proposal preserves that boundary: the CLI writes local execution and artifact evidence; it does not create a remote source of truth, grant a semantic alias, or claim custody. A future registry can promote only verified, explicitly selected artifacts from these records.

Product boundaries and hard questions¶

Avoid “magic file discovery” in v1¶

File-system tracing, process tracing, or before/after directory diffs cannot reliably determine semantic inputs and outputs. They miss remote reads, can collect enormous irrelevant trees, blur temporary files with products, and create security/privacy concerns. They are reasonable optional diagnostics only after the explicit-boundary workflow is valuable.

Separate synchronous execution from asynchronous submission¶

consist exec should initially mean that Consist observed the child process finish. sbatch, cloud submission, and queue APIs are separate adapters: record the submission as a submitted job, then attach completion/output evidence only after a monitor has observed it. A local zero exit from sbatch is not model success.

Start record-only, not cache-first¶

The existing container path already has the right ingredients for a later cacheable command contract: exact argv, digested environment identity, declared inputs, and declared outputs. But a generic host command has more uncontrolled state than a container. A cache mode should remain off until a later design defines eligible identity modes, output recovery, mutation policy, and failure semantics.

For the internal pilot only, Consist may explore an explicit --reuse-if-verified no-op mode after the comparison contract is proven. It is not the default and not a public reproducibility claim. Before declining to spawn a command, it must verify exact command and code identity, declared-input fingerprints, and the existence and current fingerprints of every declared output against a prior successful run. It must name that prior run, record that it performed verification rather than execution, and require --force to run anyway. It performs no output restoration. Commands with undeclared external side effects remain ineligible by user attestation; this is deliberately a bounded internal reuse experiment, not generic caching under another name.

Treat logs as evidence with policy controls¶

Logs often include credentials, hostnames, user paths, and large duplicated output. Provide an explicit default retention limit, redaction hooks, and an opt-out. The run record must state whether output was retained, truncated, or omitted; absence must not look like a successful capture.

Interruptions and abandoned running records¶

The wrapper should create its running record before spawning the child, handle Ctrl-C by recording the observed interruption and forwarding termination according to a documented process-group policy, and finalize logs/output checks when it remains alive. It cannot reliably finalize if it is itself SIGKILLed or the host crashes. That residual running record must be visible to existing status-reconciliation tooling; the CLI should show the exact recovery command instead of treating it as a completed or failed observation without evidence.

Smallest credible MVP¶

In scope¶

  • consist init, a .consist/ project marker, and upward project discovery from nested working directories, while retaining explicit tracker and run-directory overrides.
  • A consist exec CLI command with --input key=PATH, --output key=PATH, --outputs-dir PATH, --name, --cwd, --dry-run, --accept-suggested, explicit --shell, and -- argv separation. --outputs-dir is the onboarding/default story; keyed --output is the precise downstream handle.
  • A narrow public tracker.exec(...) used by the CLI, built directly on the existing run lifecycle. Its command, keyed input/output boundaries, environment, and working-directory parameters should align with run_container(...) where their meanings overlap, without importing image, mount, backend, or cache semantics. scenario.exec(...) follows only after the command contract has passed the pilot.
  • A local Tracker lifecycle that creates a running record before spawn, captures process outcome/interruption, hashes declared inputs/outputs, and records stdout/stderr according to policy.
  • Success only when the command exits successfully and declared outputs pass existence/admission checks; exit zero with a missing declared output is a failed run.
  • A compact comparison to the prior successful run with the same project/name, identifying changes to command/configuration, declared inputs, and declared outputs and naming the baseline run ID.
  • Failure records that retain command and process evidence without admitting nonexistent or failed outputs.
  • JSON output suitable for scripts, plus normal runs, show, artifacts, lineage, and validate usability.
  • Focused docs led by a failed/missing-output and changed-baseline example, followed by R and Julia commands; include an output-directory command and a Python example, but do not lead with Python.

Out of scope¶

  • Full filesystem/process tracing, auto-capture of dependencies, scheduler completion monitoring, automatic caching, remote execution, registry promotion, DAG orchestration, a web dashboard, configuration-file discovery, profile resolution, shared executor refactoring, scenario.exec(...), declared mutation, or delegated context handoff. These designs are retained above as explicit post-pilot increments. The narrowly attested internal --reuse-if-verified experiment is not automatic caching and requires its own admission decision after the comparison pilot.
  • Flow-slot routing is a follow-on pilot after the one-command opaque-recording contract is proven; it is not needed to establish first-command value.

Validation plan before committing to implementation¶

  1. Design spike: build a narrow tracker.exec(...) on the existing run lifecycle, a minimal consist init, and upward .consist/ discovery, without a storage-schema migration, full configuration system, or executor refactor. Exercise R/Julia-like external executable fixtures, an output-directory command, a Python script, and an expected-output failure.
  2. Failure-first and comparison demonstration: make the expected-output failure a primary example: the process exits zero, metrics.parquet is absent, and Consist records the run as failed with the exact missing-output reason and a pointer to its logs. Then rerun a named command with one changed input/configuration and show the named baseline, changed field, and output result in the compact summary.
  3. Usability study: ask 5–8 target users to record a real command. Report the count who create a valid record, the time to first valid record, and each observed declaration failure mode; do not turn this small sample into a noisy percentage claim. Include nested-directory discovery, --outputs-dir, and suggested-input acceptance in the observed setup friction.
  4. Trust tests: verify quoting/argv preservation, no shell injection in the default mode; explicit-shell recording; nonzero exit capture; signal interruption; missing output; suggested-input exclusions and explicit promotion; comparison-baseline selection; secret-redaction behavior; dirty Git identity behavior; and wrapper interruption/orphan reconciliation.
  5. Internal reuse decision: only after the comparison tests pass, decide whether an internal --reuse-if-verified pilot is worth its separate contract. Test exact identity checks, output re-fingerprinting, explicit --force, a recorded no-op outcome, and rejection for un-attested external side effects. Do not present its results as a public cache guarantee.
  6. Mutation cost measurement: measure full pre/post hashing on representative simulation checkpoint stores (such as ActivitySim pipeline.h5 / pipeline.parquet from calibration resume trials). Verify transition artifact creation, advisory locking, and whether full SHA-256 digests remain performant on multi-gigabyte files.
  7. Config adapter & override execution test: validate tracker.exec_with_config_overrides with an external simulator CLI (such as ActivitySim). Assert overlay directory materialization, argv template interpolation (-c {selected_root_dir}), zero-exit checks, declared output admission (final_trips.csv), and single-record binding of config identity with command execution facts.
  8. Composition increment: only after opaque command recording passes, run a cacheable Python → command → cacheable Python scenario. Assert sibling parentage, exact artifact lineage, output-set admission, and that a command's record-only status does not disable reuse of adjacent native steps.
  9. Configuration increment: only if pilot evidence identifies repeated operational flags as real friction, test config discovery, precedence, relative-path anchoring, profiles, source reporting, and absence of accidental cache misses.
  10. Flow-routing pilot: after opaque recording passes, run a three-command terminal flow. Verify exact slot resolution, explicit staging, single-write slots, append-only replacement history, retry/parameter-sweep usability, parallel ambiguity failures, and ordinary artifact lineage from each consumer to its producer.
  11. Boundary tests: prove that no cache hit, global registry alias, remote publication, delegated child relationship, or “reproducible” claim appears from v1 records alone. A flow-local alias must never masquerade as a global semantic alias.
  12. Decision gate: proceed only if users can create accurate records for their real commands with little setup and the resulting lineage answers a question they otherwise could not answer from shell history and directories.

Success criteria¶

The feature is promising if it achieves all of the following in a pilot:

  • Report how many of the 5–8 target users create one valid record for a real command without code changes, together with concrete declaration failures and the time to correct them.
  • Most pilot records have inputs and outputs that users later judge complete enough to explain the result; incompleteness is visibly represented rather than silently hidden.
  • Users use the compact named-run comparison to answer a concrete “what changed since the last baseline?” question, and at least two independently use show to inspect the cited run evidence.
  • The failure-first example demonstrates that a zero-exit command with a missing declared product is rejected rather than recorded as a successful result.
  • Users can find the same local tracker from a nested directory and can either declare or explicitly accept suggested input paths without mistaking a suggestion for automatic dependency capture.
  • At least one repeated role/name pattern provides concrete evidence for a registry alias or admission feature, rather than a hypothetical one.
  • No pilot user is misled into thinking Consist captured all dependencies, guaranteed replay, made a scheduler-submitted model run complete, or turned the internal reuse experiment into a general cache guarantee.

Decision requested after exploration¶

Authorize a narrowly bounded, internal-first prototype and pilot, with the record-only contract above. Its public-facing JOSS and conference story is explicit boundaries, verified results, and named-run comparison—not automatic dependency capture or caching. Do not authorize registry expansion, generic caching, filesystem tracing, full configuration-file discovery, executor refactoring, terminal flows, declared mutation, or delegated execution as part of that prototype.

If the pilot passes the usability and trust gates, the next planning document should specify the public CLI contract, execution-record schema, log-retention policy, and migration path to the existing container and Tracker.run(...) implementations.
